# Project Delivery

Apply only to new applications or explicit substantial/end-to-end documentation-dependent delivery, including authorized continuation. Ordinary bounded native work and context retrieval alone do not require this procedure, a baseline or extra approval. When applicable, preserve whole-boundary readiness before app code and final reconciliation of every affected owner.

Accept an explicit goal with existing artifact paths, or `resume [handoff-path]`. Loading this procedure is not execution authorization. Match documentation and review depth to the real boundary; a small change does not need a full-app pipeline. Use current native OMP permissions, tools and approval rather than introducing an engine or another approval ritual.

## Establish the current boundary

1. Read applicable project instructions, supplied facts and existing requirement/design/plan owners. Preserve unrelated user changes. For a new app or substantial delivery, load [documentation baseline](references/documentation-baseline.md). Check `docs-engineering` is separately enabled and available before loading its baseline-selection/context capability. Never file-load or set up a disabled/unavailable dependency: report the affected explicitly requested documentation-first result as incomplete, while ordinary native work remains permitted. Safe provisional inspection can proceed without a manifest.
2. For `resume`, load [resumption](references/resumption.md) before dependent work. A read/load-only handoff request belongs to `skill://workflow-handoff-read`, not this execution branch.
3. Separate already observed acceptance, partial implementation, remaining acceptance and missing evidence. Do not replay completed stages simply because this is a fresh session. Missing material context or authorization blocks its dependent mutation, not unrelated safe inspection.

## Delivery procedure

1. **Specify the outcome.** Load [specification](references/specification.md). Synthesize supplied facts and inspected sources; do not re-interview for known answers. Use `skill://workflow-brainstorming` only for unresolved consequential behavior. Extend the existing canonical product/requirement/design owner. For adopted projects resolve exact destinations through `skill://docs-engineering/references/locations.md` and the manifest; before adoption respect existing owners without implicit migration. Do not establish a competing spec owner. In native Plan Mode keep checkout files read-only and return proposed content through its allowed channel.
   **Exit:** observable acceptance, constraints, boundaries/errors and non-goals are explicit; consequential choices have actual authorization, not a draft's “approved” label.
2. **Resolve UI evidence only when affected.** Follow the managed AGENTS UI routing and its primary Impeccable workflow. Start with the approved project design and actual incumbent states; account for relevant empty/loading/error, accessibility and narrow/wide behavior. OpenDesign generation/refinement is a prerequisite only when the user or established project contract specifically requires it. Record that exact requirement before treating unavailable service access as a blocker. Do not demand MCP credentials or a new external artifact for ordinary approved in-place UI work. A scope-changing design requires native reapproval.
   **Exit:** required UI baseline evidence is sufficient for the selected delivery boundary. An unresolved required UI baseline blocks production implementation of that boundary, not safe inspection or authorized document/design work. Unrelated ordinary native tasks remain permitted.
3. **Prepare and review the complete baseline, then plan delivery.** Follow [documentation baseline](references/documentation-baseline.md) in information-prerequisite order, reusing its selected owners and readiness record. Load [planning](references/planning.md). Tie every material criterion to a complete vertical slice and observable proof; include exact interfaces, prerequisites, errors and irreversible choices. Plan document preparation before any app implementation, with a real end-to-end tracer only after whole-boundary readiness. For consequential multi-slice work load `skill://docs-plan-review` before native proposal/reapproval and use a fresh source-inspecting read-only worker for meaningful checking. Review exact baseline content and implementation plan together through native approval, once when that covers both. Preserve the native operative plan; persist a repository mirror only where existing convention, team or portability needs warrant it. After authorization, persist exact necessary reviewed baseline content before code. A content mirror is not approval evidence.
   **Exit:** every selected required pre-code owner is substantive, consistent and reviewed; full acceptance is planned, dependencies feasible, and independently trusted current authorization covers the exact baseline decisions and implementation scope.
4. **Implement the next authorized slice.** Read its plan, reviewed baseline anchors and affected code/tests; preserve useful real partial progress. Use [implementation brief](references/implementation-brief.md) when dispatching through actual available OMP task interfaces; delegation is optional and cannot bypass readiness. One integration owner controls shared writes and final checks. Workers do not run verification unless explicitly assigned. Use `skill://code-tdd` only for requested/approved test-first, `skill://code-debugging` for difficult diagnosis and `skill://code-review` for requested/consequential correctness/spec review. Focused security and explicit audits load their distinct owners, not a universal audit. Load [review feedback](references/review-feedback.md) when findings arrive. Material changes to reviewed requirements, architecture/interfaces, security/platform rules or scope follow [changes during implementation](references/documentation-baseline.md#changes-during-implementation): update intended owners/plan and obtain native reapproval before dependent code. Corrections within unchanged intent may use current scope.
   **Exit:** the complete slice and all affected callers/docs/tests are implemented within the authorized boundary; actual evidence, gaps and feedback dispositions are recorded.
5. **Prove acceptance and reconcile every affected document.** Load [verification](references/verification.md) and [as-built reconciliation](references/documentation-baseline.md#as-built-reconciliation). The integration owner assesses the complete boundary after workers land through authorized actual checks. Incomplete reports or source shape cannot satisfy behavioral acceptance. Record failures/unrun checks. Inspect and reconcile all affected selected product/requirement, architecture/ADR, design/contract, data/security/platform, verification/trace, release/configuration/recovery/operations and user owners as applicable, not only the app guide. Create a guide only for an unmet real reader need. Do not label proposed behavior shipped.
   **Exit:** every required criterion has relevant observed evidence, end-to-end consumers work, and all affected canonical owners/links/states accurately describe the verified result and unresolved limits.

## Reporting and interruption

Return the acceptance-to-evidence result, actual changes, observed checks/outcomes and unresolved blockers; distinguish source inspection from exercised behavior. Retain relevant unchanged observed evidence without gratuitous replay, but invalidate it when its material basis changes. Explicit pause/export uses `skill://workflow-handoff`; requested learning extraction uses `skill://workflow-retrospective`. No automatic commits, worktrees, tracker publishing, job restarts, new state database or provider/model changes.
