# Documentation-first delivery baseline

## Applicability and authority

Apply this procedure to new applications and substantial delivery handled by enabled, available `project-delivery`, including authorized continuation of that boundary. A genuinely small bounded change uses native workflow and updates only materially affected source documentation. The baseline covers the complete currently authorized delivery boundary, not merely its first tracer or worker slice. A genuinely separate boundary requires a real scope decision, not silent reduction to evade app-level information.

This is local delivery policy, not ISO-prescribed waterfall, formal conformity or runtime enforcement. Loading a skill, completing review or writing `approved` grants no execution permission. Native permissions and independently trusted current authorization still bind the exact content, plan and scope.

Native Plan Mode never writes checkout documents or code. Propose substantive baseline content through the allowed session-local/plan channel. After current authorization, persist the exact necessary reviewed baseline content before app code. Material post-approval document/design decisions require native reapproval before dependent implementation, not a hidden second approval system. One native approval may cover the exact reviewed baseline and implementation plan together.

Before readiness, allow source inspection and authorized document/design-artifact work only for this delivery. Do not retain app source, tests, scaffolding or runtime-configuration changes, install app dependencies, migrate the app or start app services. Document work grants no implicit tool setup, download or service permission. Preserve real pre-existing work. Do not block unrelated ordinary native tasks or reactivate a disabled/unavailable suite. An explicitly requested documentation-first delivery with missing procedure/material sources remains incomplete until those inputs or a revised user scope are available.

## Select and prepare the baseline

Check `engineering-docs` is separately enabled and available before loading its selection capability. Use its existing [profiles](../../engineering-docs/references/profiles.md), [manifest v1](../../engineering-docs/references/manifest.md), catalog and owner checklists. Always select and document the baseline for this scope: reuse a valid sufficient index/manifest; otherwise, when authorized, create `docs/engineering-docs.yaml` using manifest v1. Safe provisional inspection remains possible without it.

An existing non-manifest index is sufficient only if it records the same delivery-relevant owner/anchor, applicability/omission, prerequisite, review and source-basis information. Do not add another index for a preferred filename. Preserve and report invalid, unreadable, unsupported or ownership-ambiguous manifests; resolve their specific issue under current authorization. Do not bypass them with another index or silently convert YAML.

These ordered stages require logical information coverage, not separate files. A lean app may combine substantive sections in README; split only for actual ownership, audience or lifecycle. If a new file is necessary and no convention exists, use `docs/<family>/<canonical-id>.md`. Do not create a competing `docs/specs` owner where product/requirements already cover the scope.

Start security classification/requirements at stages 0/2, not a late security phase. Independent requirement/test-strategy sections can be drafted after stable purpose inputs; independent design/release/user sections after sufficient relevant architecture inputs. Review consumed prerequisites before downstream commitment. Numeric catalog phases are not execution order: verification reports and user/release plans have different planned versus observed content.

Retain the four profiles. Choose lean only from inspected genuinely low-complexity/risk scope; standard for ordinary substantial production applications; controlled for actual named signoff/baseline/full-trace obligations; regulated only for identified regulatory obligations. Types alone do not imply regulation. Lean reduces file count/detail, not necessary behavior/design/security/proof coverage. Existing suitable project rigor governs. Inline links can provide lean trace; explicit maps remain where current risk/rigor calls for them. Pre-code trace allocates requirements to architecture/design and planned test sources, never invented implementation nodes, timestamps or passed evidence.

## Before-code readiness

Record a short inspection-backed table in the existing plan/review owner, not new manifest fields or a task database:

`Information/criterion | Canonical owner/anchor | Source basis and prerequisite sufficiency | Review/disposition and gap | Evidence due now or later`

Examine content, not filenames or statuses. Every selected required pre-code item needs one sufficient accessible owner, resolved material choices/conflicts, relevant source freshness, complete negative behavior, design/verification allocation and reviewed dispositions. Optional unrelated views may be omitted with rationale. Required unfinished architecture/contracts cannot be bypassed because a tracer is possible. Standards access limits alone do not defeat voluntary alignment; missing interpretation of an actual binding obligation blocks its dependent commitment.

Keep document knowledge validation, implementation acceptance and current permission separate. Review baseline and implementation plan together through native approval. Independent review is conditional on existing consequential multi-slice scope, not a mandatory fleet. Actual trusted authorization must cover the material baseline decisions and plan. An inaccessible approval locator or unresolved material fact cannot be repaired with a marker. Document-drafting authorization is not production-code authorization. Do not add a ceremony where one native approval already covers exact reviewed content and implementation.

## Changes during implementation

Before changing a material requirement, architecture/interface, security/platform rule or approved scope, identify affected owners, update/propose intended content, resolve cross-owner conflicts and revise the plan. Obtain existing required native reapproval before dependent code. Use authorized `create`/owner-extension for changed intended design; `maintain` still distinguishes observed as-built facts. Corrections within unchanged reviewed intent may proceed under their existing scope. Invalidate only materially affected evidence. Never lower intended acceptance to agree with code. Reversible internal changes are still subject to this rule when they materially change reviewed intent.

## As-built reconciliation

After each material verified change and at final delivery, inspect every affected selected owner: product/requirements, architecture/ADRs, detailed design/native contracts, data/security/platform, verification/trace, release/configuration/migration/rollback, operations/recovery and user docs as applicable. Compare actual sources and relevant exercised evidence. Update accurate descriptive content, retain real unresolved acceptance/limits, and repair affected links/owner states only to supported levels.

Actual tests, review findings, releases, incidents, restore and store outcomes are recorded only after observation. Do not create fictional result logs or postmortems. Final app completion requires both every required criterion satisfied and complete affected-document reconciliation. Source-inspected as-built facts may be stated as such; missing required runtime/deployment evidence remains unverified. A guide update, code-complete slice or worker summary alone cannot establish full app completion.
