# Technical review and disposition

Load when a review or plan challenge supplies feedback. The delivery owner adjudicates against current canonical requirements and actual code; a reviewer is not an approval authority. Default feedback evaluation is read-only. Corrections require current implementation authorization.

1. Read all findings and their exact scope/source basis. Restate the alleged violated behavior, not just the suggested edit. Identify relationships: an unclear finding blocks related fixes, not unrelated authorized work.
2. Inspect the decisive code, callers and strongest controls; compare the requirement and platform/deployment constraints. Research why the current implementation exists. Do not accept a claim merely because several reviewers agree, or reject it because it is inconvenient.
3. Determine the real consequence. A speculative abstraction, unused professionalization feature or stylistic preference is not a correctness requirement. If a suggestion conflicts with intended behavior/security/approved scope, state the conflict and needed decision; do not let the suggestion silently rewrite the contract.
4. Record each finding using its stable identifier/source locator, alleged invariant, inspected evidence, disposition and rationale. Use `accepted`, `rejected`, `deferred` or `needs-evidence` for feedback adjudication. These are not the separate security candidate lifecycle. Accepted changes name the owning plan/slice and acceptance/proof update. Rejection names disproof; deferral names its concrete authorized future boundary and preserves unmet acceptance; needs-evidence names the decisive missing fact and safe next evidence.
5. Incorporate every actionable accepted item into the executable plan, not only a separate report. Preserve earlier rounds with their source basis; mark a new decision as superseding an old one instead of silently rewriting history. No commit is required to anchor a review: use an accessible exact content/version basis.
6. For material scope, security contract or one-way changes, obtain native reapproval of the changed exact basis before dependent mutation. Otherwise implement authorized corrections in a causal order; blocking correctness/security defects come before independent cleanup. Do not add scope to appear agreeable.
7. Re-evaluate current code and actual correction evidence. Fix-review output accounts for every prior finding as `addressed`, `not-addressed` or `needs-evidence`, and inspects newly introduced defects. An accepted suggestion is not yet addressed; an unrelated passing test is not remediation proof. Use `skill://code-review/references/fix-review.md` when performing that review. Security findings retain `skill://engineering-docs/references/security.md`'s separate discovery/refutation lifecycle.

A concise technical answer states the disposition, consequence and evidence. There is no etiquette ban, forced praise, platform posting command or automatic comment reply. Unsupported feedback remains unresolved, not a permission to proceed or an assurance claim.
