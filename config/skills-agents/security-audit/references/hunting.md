# Coherent source-led hunting

## Assignment

Main supplies Objective, Scope, Constraints, Expected Result and Done When, the relevant source-grounded architecture, assigned coverage units/paths, selected companion instructions, exclusions, known previous claims and exact terminal contract. Use actual available OMP task/role schemas. Distinct fresh read-only `security-reviewer` instances own source discovery and refutation; do not use an advice-only advisor as a source inspector. A worker never delegates or performs target execution.

Assign a coherent boundary and its dependent controls, not arbitrary file shards. Prioritize low-trust entry, valuable protected assets, changed-source paths and known coverage gaps. Limited review leaves explicit uninspected/deferred units; it never lowers the evidence bar or becomes whole-app assurance.

## Discovery loop

1. Name the lower-trust actor and starting capability, accepted input/action, protected resource and intended invariant.
2. Read the complete relevant path through parsing, normalization, identity, authorization, state/copies and the final sink. Locate the last trusted decision and compare its guarantee with the consumer's assumption.
3. Inspect sibling, batch, legacy, retry, cancellation, error, migration and restore paths that can reach that boundary. Limit depth to the assigned path and its guarantees; stop when the invariant is settled either way.
4. Test reasoning against accepted sad states: missing/empty/duplicate, stale/revoked, encoding/unit disagreement, partial failure, concurrent check/use, recovery. Do not assume the interface accepts an input merely because it is interesting.
5. Read strongest preventing controls and establish every prerequisite of a chained claim. A failed prerequisite disproves that chain; an unknown decisive runtime fact is named, not guessed.
6. Consolidate one source-derived root cause under one stable `rule_id`, while evidencing each variant's conditions and impact. Independent missing controls get separate IDs. Discovered different boundaries outside assignment go to Main as coverage gaps, not unauthorized work.
7. Return reviewed paths, exact partial/unavailable coverage, source checks and candidates with the shared required record fields. Discovery never assigns confirmed or severity. A meaningful no-candidate result explicitly returns `candidates: []` with actual inspected evidence.

No search match, suspicious name, missing best practice or scanner score alone is a candidate. Establish actor, boundary and possible concrete consequence. Do not execute examples to prove them, invent runtime output or treat read-only prompts as containment.

## Fresh coverage challenge

Main obtains a fresh source-inspecting read-only challenge of the current map/coverage evidence. The challenger reads relevant entry/control source and looks for unmapped surfaces, unchecked parallel paths, missed lifecycle modes, unjustified class exclusions and units closed without actual evidence. This is coverage critique, not independent disposition of someone else's vulnerability.

Main records each accepted gap and its source basis, preserving earlier attempts and their observed owners/evidence. New work within current authorization may be assigned; out-of-scope work remains explicitly excluded until approval changes. A bounded partial audit can finish with gaps disclosed, but cannot claim complete coverage. Missing a fresh challenge is an assessment limitation, not an inferred clean result. Follow [validation and reporting](validation-and-reporting.md) for candidate acceptance.
